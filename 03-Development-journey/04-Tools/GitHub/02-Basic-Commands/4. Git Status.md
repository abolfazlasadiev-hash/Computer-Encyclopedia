## 1. Overview

The `git status` command displays the current state of your Git working directory and staging area.

It helps you understand which files have been modified, which files are staged for the next commit, and which files are not yet tracked by Git.

`git status` is one of the most frequently used Git commands because it helps you understand what is happening in your repository before making changes or creating commits.

### Why Is `git status` Important?

You can use `git status` to:

- Check whether your working directory contains uncommitted changes.
    
- Identify modified files.
    
- Identify untracked files.
    
- See which changes are staged for the next commit.
    
- Check the current branch.
    
- See whether your local branch is ahead of or behind its remote branch.
    
- Verify whether your working directory is clean before switching branches or committing.
    

**Important:** `git status` does not modify your files, stage changes, or create commits. It only reports the current state of your repository.

---

## 2. Key Concepts

To understand `git status`, you need to understand how Git tracks changes.

### 2.1. Working Directory

The working directory is the folder containing the files you work on.

When you create, edit, or delete files, those changes initially happen in your working directory.

Example:

```
my-project/
├── .git/
├── README.md
├── index.html
└── style.css
```

### 2.2. Staging Area

The staging area is where you prepare changes before creating a commit.

You can add changes to the staging area using:

```
git add <file>
```

Files in the staging area are ready to be included in the next commit.

### 2.3. Repository

The repository stores Git's version history and metadata.

The `.git` directory contains information about commits, branches, references, and other repository data.

### 2.4. Untracked Files

An untracked file is a file that Git is not currently tracking.

For example, if you create a new file:

```
touch notes.txt
```

Git will identify it as untracked until you add it to the staging area.

### 2.5. Modified Files

A modified file is a tracked file whose content has changed since the version recorded in the index or the latest commit.

For example, editing an existing `README.md` file creates a modification.

### 2.6. Staged Changes

Staged changes are changes that have been added to the staging area.

They are prepared for the next commit.

Example:

```
git add README.md
```

### 2.7. Unmerged Files

Unmerged files occur when Git cannot automatically resolve conflicting changes during a merge or another operation that combines changes.

Git requires you to resolve these conflicts before completing the operation.

---

## 3. Syntax

The basic syntax is:

```
git status [options]
```

|Argument|Description|
|---|---|
|`git status`|Displays the current repository status.|
|`options`|Optional flags that change the output format or behavior.|

You can run `git status` from any directory inside a Git repository.

---

## 4. Commands

### 4.1. Display the Current Repository Status

```
git status
```

Displays detailed information about the working directory and staging area.

Example output:

```
On branch main

Changes not staged for commit:
  modified:   README.md

Untracked files:
  notes.txt

no changes added to commit
```

This means:

- You are currently on the `main` branch.
    
- `README.md` has been modified but is not staged.
    
- `notes.txt` is a new, untracked file.
    
- No changes have been staged for the next commit.
    

### 4.2. Display Short Status

```
git status --short
```

Or:

```
git status -s
```

This displays a compact version of the repository status.

Example:

```
 M README.md
?? notes.txt
```

The two-character status codes represent the state of each file.

### 4.3. Understand Status Codes

Git uses two status columns:

```
XY filename
```

- `X` represents the status of the file in the staging area (index).
    
- `Y` represents the status of the file in the working tree.
    

Common status codes:

|Code|Meaning|
|---|---|
|`??`|Untracked file.|
|`M`|Modified in the working tree, not staged.|
|`M`|Modified and staged.|
|`A`|New file added to the staging area.|
|`D`|File deleted and staged.|
|`D`|Tracked file deleted in the working tree, not staged.|
|`R`|File renamed and staged.|
|`C`|File copied and staged.|
|`MM`|File has staged changes and additional unstaged changes.|
|`AM`|File was added to the staging area and then modified again.|

**Note:** The first column represents the staging area, and the second represents the working tree. A space means there is no change in that position.

### 4.4. Display Branch Information

```
git status --branch
```

Or:

```
git status -b
```

Displays branch information along with the working tree status.

For example:

```
## main
nothing to commit, working tree clean
```

### 4.5. Display Short Status with Branch Information

```
git status -sb
```

This combines short output with branch information.

Example:

```
## main
 M README.md
?? notes.txt
```

### 4.6. Display Status Without Untracked Files

```
git status --untracked-files=no
```

This hides untracked files from the output.

It does not delete or ignore those files. They remain in your working directory.

### 4.7. Display All Untracked Files

```
git status --untracked-files=all
```

This displays individual untracked files, including files inside untracked directories.

### 4.8. Display Ignored Files

```
git status --ignored
```

This includes files ignored by Git's ignore rules.

Example:

```
Ignored files:
  .env
  node_modules/
```

Use this option when you want to verify which files are being ignored.

### 4.9. Display Status in a Specific Format

```
git status --porcelain
```

This produces a stable, machine-readable output format.

It is particularly useful in scripts and automation.

Example:

```
 M README.md
?? notes.txt
```

You can also use:

```
git status --porcelain=v1
```

The `v1` format is useful when scripts need a predictable status representation.

### 4.10. Display Detailed Branch Tracking Information

```
git status -sb
```

If your local branch tracks a remote branch, Git may display information such as:

```
## main...origin/main [ahead 2, behind 1]
```

This means:

- Your local branch is two commits ahead of `origin/main`.
    
- Your local branch is one commit behind `origin/main`.
    

The comparison depends on the latest remote-tracking information available locally. Run `git fetch` to update that information.

## 5. Examples

### Example 1: Check a Newly Initialized Repository

Run:

```
git init my-project
cd my-project
git status
```

You may see:

```
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)
```

This means the repository has been initialized but does not contain any commits.

The initial branch name may differ depending on your Git configuration.

### Example 2: Check an Untracked File

Create a new file:

```
touch notes.txt
```

Then run:

```
git status
```

Example output:

```
Untracked files:
  notes.txt

nothing added to commit but untracked files present
```

Git recognizes that the file exists but is not tracking it yet.

### Example 3: Check a Modified File

Edit an existing tracked file, such as `README.md`.

Then run:

```
git status
```

Example output:

```
Changes not staged for commit:
  modified: README.md
```

The file has changed, but the changes have not been staged.

### Example 4: Check a Staged File

Run:

```
git add README.md
git status
```

Example output:

```
Changes to be committed:
  modified: README.md
```

The changes are now staged and ready for the next commit.

### Example 5: Check Staged and Unstaged Changes

First, modify a file and stage it:

```
git add README.md
```

Then modify the same file again without staging the second modification.

Run:

```
git status --short
```

Example output:

```
MM README.md
```

This means:

- The first modification is staged.
    
- An additional modification exists in the working directory and is not staged.
    

### Example 6: Check Whether the Working Directory Is Clean

Run:

```
git status
```

If there are no pending changes, Git displays:

```
On branch main

nothing to commit, working tree clean
```

This means there are no staged or unstaged changes and no untracked files being reported.

## 6. Common Errors

### 6.1. Not a Git Repository

Example:

```
fatal: not a git repository (or any of the parent directories): .git
```

This means Git cannot find a repository in the current directory or its parent directories.

**Possible causes:**

- You are outside a Git repository.
    
- You have not initialized the project with `git init`.
    
- You are in the wrong directory.
    

**Solution:**

Navigate to the correct directory:

```
cd my-project
```

If the project is not yet a Git repository, initialize it:

```
git init
```

### 6.2. Unexpected Untracked Files

You may see files that you do not want Git to track.

**Solution:**

If those files should always be excluded from Git, add appropriate patterns to `.gitignore`.

Example:

```
node_modules/
.env
*.log
```

Then run:

```
git status
```

**Note:** `.gitignore` does not automatically stop tracking files that Git already tracks.

### 6.3. Changes Are Not Appearing as Expected

Possible causes:

- You are checking the wrong repository.
    
- The file is ignored by Git.
    
- The file has not actually changed.
    
- The file is already staged, so its status appears in a different section.
    

**Solution:**

Run:

```
git status --short
git status --ignored
```

You can also inspect differences with:

```
git diff
git diff --cached
```

### 6.4. Branch Information Is Missing or Unexpected

Possible causes:

- The repository has no commits yet.
    
- You are working in a detached HEAD state.
    
- The branch does not have an upstream tracking branch.
    

**Solution:**

Check the current branch:

```
git branch --show-current
```

Check branch details:

```
git branch -vv
```

## 7. Best Practices

1. **Run** `**git status**` **frequently:** Check the repository state before and after important operations.
    
2. **Check before committing:** Make sure you understand which files are staged.
    
3. **Use short status for quick checks:** `git status -sb` provides concise information.
    
4. **Review untracked files:** Make sure you do not accidentally include sensitive or unnecessary files.
    
5. **Use** `**.gitignore**` **appropriately:** Exclude generated files, dependencies, logs, and local configuration files when appropriate.
    
6. **Inspect staged changes:** Use `git diff --cached` before creating a commit.
    
7. **Understand status codes:** Learn the difference between staged and unstaged modifications.
    
8. **Check branch information:** Make sure you are working on the correct branch.
    
9. **Fetch before interpreting remote status:** Use `git fetch` to refresh remote-tracking information when checking whether your branch is ahead or behind.
    
10. **Use porcelain output in scripts:** Prefer `git status --porcelain` for automation rather than parsing human-readable output.
    

### Recommended Workflow Before Committing

```
# Check repository status
git status

# Stage the intended changes
git add README.md

# Check the staged changes
git status

# Review staged differences
git diff --cached

# Create a commit
git commit -m "Update README"
```

## 11. Final Summary

The `git status` command helps you understand the current state of your Git repository.

It identifies:

- Untracked files.
    
- Modified files.
    
- Staged changes.
    
- Deleted files.
    
- Merge conflicts.
    
- Current branch information.
    
- Differences between local and remote-tracking branches.
    

The most important commands to remember are:

```
# Display repository status
git status

# Display short status
git status -s

# Display status with branch information
git status -sb

# Display ignored files
git status --ignored

# Display machine-readable status
git status --porcelain
```

**Key takeaway:** Use `git status` frequently to understand what has changed, what is staged, and what is ready to be committed. It is one of the most important commands in a safe and effective Git workflow.
