## 1. Overview

The `git add` command is used to add changes from the working directory to the staging area (also called the index).

In Git, changes are not automatically included in the next commit. You must first stage the changes you want to save.

The `git add` command allows you to select specific files or groups of changes before creating a commit.

### Why Is `git add` Important?

You can use `git add` to:

- Stage new files.
    
- Stage modified files.
    
- Stage deleted files.
    
- Select specific changes for the next commit.
    
- Prepare multiple files for a single commit.
    
- Control exactly which changes will be included in a commit.
    

**Important:** `git add` does not create a commit. It only prepares changes for a future commit.

---

## 2. Key Concepts

Before using `git add`, you should understand the following Git concepts.

### 2.1. Working Directory

The working directory is where you create, edit, and delete project files.

For example:

```
my-project/
├── README.md
├── index.html
└── style.css
```

When you modify these files, Git detects the changes but does not automatically stage them.

### 2.2. Staging Area

The staging area is an intermediate area where you prepare changes before committing them.

You can think of it as a selection of changes that will be included in your next commit.

The staging area is also called the **index**.

### 2.3. Repository

The repository stores the project's version history.

When you run `git commit`, Git creates a commit from the changes currently staged in the index.

### 2.4. Untracked Files

An untracked file is a new file that Git has not started tracking.

Example:

```
touch notes.txt
```

Git identifies `notes.txt` as untracked.

You can begin tracking it by staging it:

```
git add notes.txt
```

### 2.5. Modified Files

A modified file is an existing tracked file whose content has changed.

Example:

```
# Edit README.md, then stage it
git add README.md
```

### 2.6. Staged Changes

Staged changes are changes that have been added to the index and are ready for the next commit.

You can inspect them with:

```
git status
```

And review their content with:

```
git diff --cached
```

### 2.7. Staging Is Not Committing

The difference is important:

- `git add` prepares changes.
    
- `git commit` saves staged changes as a new commit.
    

You can stage changes from several files and create one commit containing all of them.

---

## 3. Syntax

The basic syntax is:

```
git add [options] <pathspec>...
```

|Argument|Description|
|---|---|
|`git add`|Adds changes to the staging area.|
|`options`|Optional flags that control what gets staged.|
|`pathspec`|A file, directory, or pattern identifying what to stage.|
|`...`|Indicates that multiple paths can be provided.|

Examples:

```
git add README.md
git add README.md style.css
git add .
```

---

## 4. Commands

### 4.1. Stage a Specific File

```
git add README.md
```

Stages changes from `README.md`.

This is useful when you want to commit only selected files.

### 4.2. Stage Multiple Files

```
git add README.md index.html style.css
```

Stages changes from all three specified files.

### 4.3. Stage All Changes Under the Current Directory

```
git add .
```

Stages changes under the current directory, including new files, modifications, and deletions.

The scope is important: running this command from a subdirectory generally limits its effect to that directory and its descendants.

### 4.4. Stage All Changes in the Repository

```
git add -A
```

Or:

```
git add --all
```

Stages all changes throughout the repository, including:

- New files.
    
- Modified files.
    
- Deleted files.
    

This is useful when you want to prepare all repository changes for a commit.

### 4.5. Stage Only Tracked Files

```
git add -u
```

Stages modifications and deletions of files Git already tracks.

It does not stage new, untracked files.

This is useful when you want to update tracked files without adding newly created files.

### 4.6. Stage a Specific Directory

```
git add src/
```

Stages changes under the `src/` directory.

Example project:

```
my-project/
├── README.md
├── src/
│   ├── app.js
│   └── utils.js
└── tests/
    └── app.test.js
```

Running:

```
git add src/
```

Stages changes under `src/` without selecting unrelated changes elsewhere.

### 4.7. Stage Files Using Wildcards

```
git add "*.js"
```

This stages files matching the specified pattern according to Git's pathspec rules.

You can also use patterns such as:

```
git add "*.css"
git add "*.md"
git add "src/*.js"
```

**Note:** Wildcard expansion can be handled by your shell or by Git, depending on the pattern and how it is quoted. Quoting patterns allows Git to interpret them as pathspecs.

### 4.8. Stage Changes Interactively

```
git add -i
```

Starts Git's interactive staging interface.

It allows you to select files and manage staged changes through a menu.

This can be useful when working with many modified files.

### 4.9. Stage Changes in Small Sections

```
git add -p
```

The `-p` option means patch mode.

It allows you to review changes in individual sections, called _hunks_, and choose which sections to stage.

Example:

```
Stage this hunk [y,n,q,a,d,s,e,?]?
```

Common responses:

|Option|Description|
|---|---|
|`y`|Stage this hunk.|
|`n`|Do not stage this hunk.|
|`q`|Quit patch mode.|
|`a`|Stage this and all remaining hunks in the current file.|
|`d`|Do not stage this or any remaining hunks in the current file.|
|`s`|Split the current hunk into smaller hunks, if possible.|
|`e`|Manually edit the patch.|
|`?`|Display help.|

This is especially useful when one file contains several unrelated changes.

### 4.10. Stage All Changes in a Specific Directory

```
git add -A src/
```

Stages additions, modifications, and deletions under `src/`.

### 4.11. Stage a File After Deleting It

Suppose you delete a tracked file:

```
rm old-file.txt
```

Then stage the deletion:

```
git add old-file.txt
```

Alternatively, stage all repository changes:

```
git add -A
```

### 4.12. Check Staged Changes

After staging files, run:

```
git status
```

To inspect the actual staged content:

```
git diff --cached
```

You can also use:

```
git diff --staged
```

These commands show differences between the staging area and the current commit.

### 4.13. Unstage a File

If you staged a file by mistake, you can remove it from the staging area without discarding its working-directory changes.

```
git restore --staged README.md
```

To unstage all staged changes:

```
git restore --staged .
```

**Important:** These commands do not discard the changes in your working directory. They only remove the selected changes from the staging area.

## 5. Examples

### Example 1: Stage a New File

Create a file:

```
touch notes.txt
```

Check the status:

```
git status
```

You may see:

```
Untracked files:
  notes.txt
```

Stage the file:

```
git add notes.txt
```

Check again:

```
git status
```

The file should now appear under:

```
Changes to be committed:
  new file: notes.txt
```

### Example 2: Stage a Modified File

Edit an existing file:

```
# Make changes to README.md
```

Stage it:

```
git add README.md
```

Verify:

```
git status
```

The file should appear as modified and staged.

### Example 3: Stage Multiple Files

Suppose you modified two files and created another:

```
README.md
index.html
style.css
```

Stage all three:

```
git add README.md index.html style.css
```

Verify:

```
git status
```

### Example 4: Stage All Repository Changes

```
git add -A
git status
```

This stages all additions, modifications, and deletions throughout the repository.

### Example 5: Stage Only Tracked Changes

Suppose you modified `README.md` and created `notes.txt`.

Run:

```
git add -u
```

The modified tracked file is staged, but `notes.txt` remains untracked.

### Example 6: Stage Only Part of a File

Suppose you made two unrelated changes in `app.js`:

- Updated a function.
    
- Added a debugging statement.
    

You want to stage only the function update.

Run:

```
git add -p app.js
```

Review each hunk and select the changes you want to include.

Then inspect the staged result:

```
git diff --cached
```

This helps you create focused commits.

### Example 7: Stage and Commit Changes

```
# Stage the file
git add README.md

# Review staged changes
git diff --cached

# Create a commit
git commit -m "Update README"
```

The commit contains the changes that were staged when `git commit` was executed.

## 6. Common Errors

### 6.1. Nothing to Commit

Example:

```
nothing to commit, working tree clean
```

This means Git does not detect any changes to stage or commit.

**Possible causes:**

- You have not modified any tracked files.
    
- All changes have already been committed.
    
- Your changes are ignored by Git.
    

**Solution:**

Check the repository status:

```
git status
```

If you expected a file to appear, check whether it is ignored.

### 6.2. Pathspec Did Not Match Any Files

Example:

```
fatal: pathspec 'file.txt' did not match any files
```

This usually means Git cannot find the specified path.

**Possible causes:**

- The filename is incorrect.
    
- The file does not exist.
    
- You are running the command from an unexpected directory.
    
- The path is incorrect.
    

**Solution:**

Check the current directory and file names:

```
pwd
ls
git status
```

Then use the correct path.

### 6.3. Accidentally Staging Too Many Files

If you run:

```
git add .
```

You may stage files you did not intend to include.

**Solution:**

Inspect the staged changes:

```
git status
git diff --cached
```

Unstage a specific file:

```
git restore --staged file.txt
```

Or unstage all changes:

```
git restore --staged .
```

Your working-directory changes remain intact.

### 6.4. A File Is Not Being Added

A file may be ignored by Git.

Check ignored files:

```
git status --ignored
```

Check which ignore rule applies:

```
git check-ignore -v path/to/file
```

If the file should be tracked, review the relevant `.gitignore` rule.

You can force-add an ignored file:

```
git add -f path/to/file
```

Use this carefully, especially with files containing passwords, tokens, or other sensitive information.

### 6.5. Changes Are Staged but More Changes Remain

A file may have been modified after it was staged.

Example:

```
MM README.md
```

The first `M` means the file has staged changes.

The second `M` means it has additional unstaged modifications.

**Solution:**

Review both versions:

```
git diff
git diff --cached
```

Stage the remaining changes if they should be included:

```
git add README.md
```

## 7. Best Practices

1. **Stage only what you intend to commit:** Avoid adding unrelated changes.
    
2. **Review staged changes:** Use `git diff --cached` before committing.
    
3. **Use specific filenames when appropriate:** This gives you precise control over commits.
    
4. **Use** `**git add -p**` **for complex changes:** It allows you to stage only selected parts of a file.
    
5. **Understand the difference between** `**.**` **and** `**-A**`**:** Their scope can differ depending on the current directory.
    
6. **Use** `**git add -u**` **carefully:** It stages modifications and deletions of tracked files, but not new files.
    
7. **Check your** `**.gitignore**` **file:** Avoid accidentally staging generated files, dependencies, and local configuration.
    
8. **Never stage secrets:** Do not commit passwords, API keys, private keys, or access tokens.
    
9. **Check the status after staging:** Use `git status` to confirm what is staged.
    
10. **Create focused commits:** Group related changes together instead of combining unrelated work.
    

### Recommended Workflow

```
# Check the repository status
git status

# Stage specific changes
git add README.md

# Review staged changes
git diff --cached

# Check the final staging state
git status

# Create a commit
git commit -m "Update README"
```

## 11. Final Summary

The `git add` command moves selected changes from your working directory into the staging area.

It allows you to control exactly which changes will be included in your next commit.

The most important commands to remember are:

```
# Stage a specific file
git add README.md

# Stage multiple files
git add file1.txt file2.txt

# Stage changes under the current directory
git add .

# Stage all repository changes
git add -A

# Stage only tracked file changes
git add -u

# Stage selected parts of a file
git add -p

# Review staged changes
git diff --cached

# Unstage a file
git restore --staged README.md
```

**Key takeaway:** Use `git add` to carefully select and prepare changes before creating a commit. The staging area gives you control over what goes into each commit.
