
## 1. Overview

The `git diff` command is used to compare changes in a Git repository.

It shows the differences between files in your working directory, staging area, and commits.

Git Diff is an essential command for reviewing changes before staging them or creating a commit.

### Why Is `git diff` Important?

You can use `git diff` to:

- See what has changed in your files.
    
- Review modifications that have not been staged.
    
- Review changes that have already been staged.
    
- Compare two branches.
    
- Compare two commits.
    
- Compare a file with its previous version.
    
- Inspect changes before creating a commit.
    
- Understand exactly what will be included in a commit.
    

**Important:** `git diff` only displays differences. It does not modify files, stage changes, or create commits.

---

## 2. Key Concepts

To understand `git diff`, you need to understand the three main areas of a Git repository.

### 2.1. Working Directory

The working directory contains the files you are currently editing.

When you modify a tracked file, the changes exist in your working directory.

Example:

```
my-project/
├── .git/
├── README.md
├── index.html
└── style.css
```

### 2.2. Staging Area

The staging area, also called the index, contains changes prepared for the next commit.

You add changes to this area using:

```
git add <file>
```

### 2.3. Repository (HEAD)

The repository stores committed project history.

`HEAD` usually points to the current branch's latest commit.

When you run `git diff`, Git compares different versions of your files depending on the arguments you provide.

### 2.4. Unstaged Changes

Unstaged changes are modifications in your working directory that have not been added to the staging area.

Use:

```
git diff
```

to inspect these changes.

### 2.5. Staged Changes

Staged changes are modifications that have already been added to the staging area but have not yet been committed.

Use:

```
git diff --cached
```

to inspect them.

You can also use:

```
git diff --staged
```

### 2.6. Commit Comparison

Git allows you to compare two commits to understand what changed between them.

For example:

```
git diff commit1 commit2
```

This displays the differences between the two specified commits.

### 2.7. Diff Output Symbols

Git uses special symbols to represent changes.

Example:

```
- Old content
+ New content
```

|Symbol|Meaning|
|---|---|
|`+`|A line added in the newer version.|
|`-`|A line removed from the older version.|
|`@@`|Marks the beginning of a change section (hunk).|
|`---`|Identifies the old file in a diff header.|
|`+++`|Identifies the new file in a diff header.|

---

## 3. Syntax

The basic syntax is:

```
git diff [options] [<commit>] [--] [<path>...]
```

Git supports several comparison types:

```
git diff
git diff --cached
git diff HEAD
git diff <commit1> <commit2>
git diff <branch1> <branch2>
git diff -- <file>
```

|Argument|Description|
|---|---|
|`git diff`|Compares the working directory with the staging area.|
|`--cached`|Compares the staging area with the latest commit.|
|`--staged`|An alternative to `--cached`.|
|`HEAD`|Refers to the current commit.|
|`<commit>`|Specifies a commit to compare.|
|`<branch>`|Specifies a branch to compare.|
|`--`|Separates revision arguments from file paths.|
|`<path>`|Limits the comparison to specific files or directories.|

## 4. Commands

### 4.1. Show Unstaged Changes

```
git diff
```

Displays changes in tracked files that have not been staged.

Example output:

```
diff --git a/README.md b/README.md
index 1234567..abcdef0 100644
--- a/README.md
+++ b/README.md
@@ -1,3 +1,4 @@
 # My Project
-This is the old description.
+This is the updated description.
+This project uses Git.
```

Explanation:

- Lines beginning with `-` were removed.
    
- Lines beginning with `+` were added.
    
- The changes are still unstaged.
    

### 4.2. Show Staged Changes

```
git diff --cached
```

Displays changes that have been staged but not committed.

You can also use:

```
git diff --staged
```

This is particularly useful before creating a commit.

### 4.3. Compare Working Directory with the Latest Commit

```
git diff HEAD
```

Compares the working directory with the latest commit.

It includes both staged and unstaged changes to tracked files.

This is useful when you want to review all tracked changes that have not yet been committed.

### 4.4. Compare Two Commits

```
git diff <commit1> <commit2>
```

Displays the differences between two commits.

Example:

```
git diff abc1234 def5678
```

You can find commit IDs using:

```
git log --oneline
```

### 4.5. Compare Two Branches

```
git diff main development
```

Displays the difference between the tips of the two branches.

This is useful when you want to inspect how two branches differ.

**Note:** This compares the snapshots at the branch tips. It does not necessarily show only the changes introduced by one branch since the branches diverged.

### 4.6. Compare a Specific File

```
git diff -- README.md
```

Displays changes in `README.md` that are not staged.

To inspect staged changes in the same file:

```
git diff --cached -- README.md
```

The `--` separator makes it clear that the following argument is a path.

### 4.7. Compare a File Between Two Commits

```
git diff <commit1> <commit2> -- README.md
```

Displays changes to `README.md` between two commits.

Example:

```
git diff HEAD~1 HEAD -- README.md
```

This compares the file in the latest commit with its version in the previous commit.

### 4.8. Show Only Changed File Names

```
git diff --name-only
```

Displays only the names of files with unstaged changes.

For staged changes:

```
git diff --cached --name-only
```

This is useful when you only need a list of changed files.

### 4.9. Show Change Statistics

```
git diff --stat
```

Displays a summary of changes, including the number of insertions and deletions for each file.

Example:

```
 README.md  | 5 +++--
 index.html | 3 ++-
 2 files changed, 4 insertions(+), 4 deletions(-)
```

For staged changes:

```
git diff --cached --stat
```

### 4.10. Show Only Added and Deleted Line Counts

```
git diff --numstat
```

Displays the number of added and deleted lines for each changed file.

Example:

```
3       1       README.md
2       2       index.html
```

The first number represents added lines, and the second represents deleted lines.

### 4.11. Show a Word-Level Diff

```
git diff --word-diff
```

Highlights changes at the word level instead of displaying entire changed lines.

This can be useful when modifying long paragraphs or documentation.

### 4.12. Show a More Compact Diff

```
git diff --compact-summary
```

Displays a compact summary of file changes.

It can show changes such as file creation, deletion, or mode changes.

### 4.13. Ignore Whitespace Changes

```
git diff -w
```

Or:

```
git diff --ignore-all-space
```

Ignores whitespace differences when comparing files.

This is useful when formatting changes make a diff difficult to read.

Other whitespace options include:

```
git diff -b
git diff --ignore-space-at-eol
```

- `-b` ignores changes in the amount of whitespace.
    
- `--ignore-space-at-eol` ignores whitespace changes at the end of lines.
    

### 4.14. Display a Unified Diff with More Context

```
git diff -U5
```

Displays five lines of context around each change.

The default is usually three lines.

This can help you understand changes in relation to nearby code.

### 4.15. Compare Branches Using the Common Ancestor

```
git diff main...development
```

The three-dot syntax compares the common ancestor of the two branches with the tip of the second branch.

This is often useful for reviewing changes introduced by `development` since it diverged from `main`.

**Important:** This is different from:

```
git diff main development
```

The two-dot form compares the two branch tips directly, while the three-dot form compares the merge base with the second branch.

### 4.16. Check Whether a File Has Changed

```
git diff --quiet -- README.md
```

This command produces no normal diff output.

It returns an exit status:

- `0` means no differences were found.
    
- `1` means differences were found.
    

This is useful in scripts and automation.

## 5. Examples

### Example 1: Inspect an Unstaged Modification

Modify `README.md`.

Then run:

```
git diff
```

You may see:

```
- Old project description
+ New project description
```

This means the file has changed but has not been staged.

### Example 2: Inspect a Staged Modification

Stage the file:

```
git add README.md
```

Then run:

```
git diff --cached
```

You will see the changes that are ready for the next commit.

### Example 3: Compare Staged and Unstaged Changes

Suppose you modify `README.md`, stage it, and then modify it again.

Run:

```
git diff
git diff --cached
```

The first command shows the additional unstaged changes.

The second command shows the changes already staged.

### Example 4: Review All Uncommitted Tracked Changes

Run:

```
git diff HEAD
```

This shows all changes to tracked files since the current commit, including staged and unstaged changes.

### Example 5: Compare the Last Two Commits

```
git diff HEAD~1 HEAD
```

This displays the differences between the previous commit and the latest commit.

### Example 6: Compare Two Branches

```
git diff main development
```

This shows how the current contents of `main` and `development` differ.

### Example 7: Review Changes Before Committing

A useful workflow is:

```
git status

git diff

git diff --cached

git commit -m "Update project documentation"
```

This lets you review both unstaged and staged changes before creating a commit.

## 6. Common Errors

### 6.1. No Output from `git diff`

If `git diff` produces no output, it usually means there are no unstaged changes to tracked files.

Possible explanations:

- No tracked files have been modified.
    
- All modifications have already been staged.
    
- Changes are in untracked files, which ordinary `git diff` does not display.
    

**Solution:**

Check the repository status:

```
git status
```

To inspect staged changes:

```
git diff --cached
```

To see untracked files:

```
git status --short
```

### 6.2. Untracked Files Are Not Shown

By default, `git diff` does not display the contents of untracked files.

**Solution:**

Stage the file first:

```
git add new-file.txt
```

Then inspect it:

```
git diff --cached
```

If you do not want to stage it, inspect its contents using your editor or another file comparison tool.

### 6.3. Comparing the Wrong Branches

Example:

```
git diff main development
```

You may see more changes than expected because Git compares the complete snapshots at the two branch tips.

**Solution:**

If you want to inspect changes introduced by `development` since the branches diverged, use:

```
git diff main...development
```

### 6.4. Unknown Revision or Path

Example:

```
fatal: ambiguous argument 'abc1234': unknown revision or path not in the working tree.
```

Possible causes:

- The commit ID does not exist.
    
- The branch name is incorrect.
    
- The repository does not contain the specified reference.
    

**Solution:**

List available commits:

```
git log --oneline
```

List branches:

```
git branch
```

Then use a valid commit ID or branch name.

### 6.5. Diff Is Too Large

Large changes can produce a very long output.

**Solution:**

Limit the comparison to a specific file:

```
git diff -- README.md
```

Show only changed file names:

```
git diff --name-only
```

Or display a summary:

```
git diff --stat
```

## 7. Best Practices

1. **Review changes before staging:** Use `git diff` to understand your modifications.
    
2. **Review staged changes before committing:** Use `git diff --cached`.
    
3. **Check both staged and unstaged changes:** A file can contain changes in both areas.
    
4. **Use file-specific comparisons:** Avoid unnecessary output when working with large projects.
    
5. **Use** `**--stat**` **for summaries:** It provides a quick overview of changed files.
    
6. **Use** `**-w**` **when whitespace changes are distracting:** This helps focus on meaningful changes.
    
7. **Understand branch comparison syntax:** Know the difference between `git diff A B` and `git diff A...B`.
    
8. **Use** `**git diff HEAD**` **carefully:** It compares tracked working-tree content against the current commit, including staged and unstaged changes.
    
9. **Review before committing:** Make sure the staged changes match the purpose of your commit.
    
10. **Use diff output in code reviews:** It helps identify unexpected changes, mistakes, and accidental modifications.
    

### Recommended Workflow

```
# Check repository status
git status

# Review unstaged changes
git diff

# Stage intended changes
git add README.md

# Review staged changes
git diff --cached

# Create a commit
git commit -m "Update README"
```

## 11. Final Summary

The `git diff` command allows you to inspect differences between files, the staging area, commits, and branches.

It helps you understand exactly what has changed before staging or committing your work.

The most important commands to remember are:

```
# Show unstaged changes
git diff

# Show staged changes
git diff --cached

# Show all uncommitted changes to tracked files
git diff HEAD

# Compare two commits
git diff <commit1> <commit2>

# Compare two branches
git diff main development

# Show only changed file names
git diff --name-only

# Show a summary of changes
git diff --stat

# Ignore whitespace differences
git diff -w
```

**Key takeaway:** Use `git diff` to review and understand your changes before staging and committing them. It helps you create cleaner, safer, and more meaningful commits.
