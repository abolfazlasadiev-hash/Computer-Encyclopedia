## 1. Overview

The `git commit` command records staged changes in the Git repository as a new commit.

A commit represents a snapshot of your project at a particular point in time. It allows you to track the history of your project, understand what changed, and return to earlier versions when necessary.

Before creating a commit, you normally select the changes you want to include using `git add`.

### Why Is `git commit` Important?

You can use `git commit` to:

- Save staged changes in the repository history.
    
- Create a record of completed work.
    
- Describe changes using commit messages.
    
- Track the development of a project over time.
    
- Create meaningful checkpoints in your project.
    
- Collaborate with other developers.
    
- Identify when and why a particular change was introduced.
    

**Important:** A commit is stored in your local repository. Creating a commit does not automatically upload it to GitHub, GitLab, or another remote repository. To share your commits, you generally use `git push`.

## 2. Key Concepts

Before using `git commit`, you should understand the following concepts.

### 2.1. Working Directory

The working directory contains the files you are currently editing.

Changes made to files initially exist in the working directory.

### 2.2. Staging Area

The staging area, also called the index, contains the changes selected for the next commit.

You can stage changes using:

```
git add <file>
```

Git creates a commit from the staged snapshot, not automatically from every modification in your working directory.

### 2.3. Commit

A commit is a saved snapshot of the staged project state.

Each commit contains information such as:

- A unique commit identifier (hash).
    
- The author.
    
- The committer.
    
- The commit date.
    
- A commit message.
    
- A reference to its parent commit or commits.
    
- A reference to the project tree representing the snapshot.
    

### 2.4. Commit Message

A commit message describes the purpose of a commit.

Example:

```
Add user authentication
```

A good commit message explains what the change accomplishes.

### 2.5. HEAD

`HEAD` is a reference that normally identifies the currently checked-out commit.

When you create a commit while working on a branch, Git normally moves that branch's reference forward to the new commit, and `HEAD` continues to refer to that branch.

### 2.6. Parent Commit

Most commits have one parent commit.

A commit can have multiple parents, as commonly happens with merge commits.

The parent relationship connects commits and forms the repository's history.

### 2.7. Local Commit vs. Remote Commit

A local commit exists in your local repository.

A remote repository does not receive that commit until you push it.

Example:

```
git commit -m "Add login feature"
git push origin main
```

The first command creates a local commit. The second sends local commits to the remote repository.

### 2.8. Author and Committer

Git records both author and committer information.

- **Author:** The person who originally wrote the change.
    
- **Committer:** The person who created the commit.
    

These are often the same person, but they can differ when changes are applied or transferred by someone else.

## 3. Syntax

The basic syntax is:

```
git commit [options]
```

Common forms include:

```
git commit -m "Commit message"
git commit
git commit -a -m "Commit message"
git commit --amend
```

|Argument|Description|
|---|---|
|`git commit`|Creates a commit from staged changes.|
|`-m`|Specifies the commit message directly.|
|`-a`|Automatically stages modifications and deletions of tracked files before committing.|
|`--amend`|Replaces the latest commit with a new commit.|
|`--allow-empty`|Creates a commit even when there are no changes.|
|`--no-verify`|Skips configured pre-commit and commit-message hooks.|
|`--author`|Overrides the author information.|

## 4. Commands

### 4.1. Create a Commit with a Message

```
git commit -m "Initial commit"
```

Creates a commit using the staged changes and the supplied message.

The `-m` option allows you to write the commit message directly in the terminal.

### 4.2. Create a Commit Without the `-m` Option

```
git commit
```

Git opens the configured text editor so you can write a commit message.

After saving and closing the editor, Git creates the commit if the message is valid and the operation succeeds.

### 4.3. Create a Commit with a Multi-Line Message

```
git commit -m "Add user authentication" -m "Implement login and logout functionality."
```

The first `-m` provides the subject.

The second `-m` adds a separate paragraph to the commit message body.

A multi-line message can also be written in the editor:

```
Add user authentication

Implement login and logout functionality.
Add validation for user credentials.
```

### 4.4. Automatically Stage Tracked File Changes

```
git commit -a -m "Update documentation"
```

The `-a` option automatically stages modifications and deletions of tracked files before creating the commit.

**Important:** It does not automatically include new, untracked files.

For example, if you modify `README.md` and create `notes.txt`, this command includes the modification to `README.md` but not the new `notes.txt`.

To include a new file, stage it explicitly:

```
git add notes.txt
git commit -a -m "Update documentation"
```

### 4.5. Commit All Intended Changes

A common workflow is:

```
git add -A
git commit -m "Update project files"
```

The first command stages all changes in the repository.

The second command creates a commit from those staged changes.

Review the staged changes before committing when possible:

```
git diff --cached
```

### 4.6. Amend the Latest Commit

```
git commit --amend
```

This replaces the latest commit with a new commit that incorporates the current staged changes.

Git opens the editor so you can modify the commit message.

To amend the latest commit using a new message:

```
git commit --amend -m "Improve login validation"
```

To add staged changes to the latest commit without changing its message:

```
git commit --amend --no-edit
```

**Important:** Amending creates a replacement commit with a different commit ID. Avoid amending commits that have already been shared with others unless you understand the consequences of rewriting history.

### 4.7. Create an Empty Commit

```
git commit --allow-empty -m "Trigger deployment"
```

Creates a commit even when there are no staged changes.

This can be useful for triggering CI/CD pipelines or recording an intentional event.

### 4.8. Override the Author

```
git commit --author="John Doe <john@example.com>" -m "Update configuration"
```

This sets the author information for the new commit.

The committer information is still determined by Git's configuration and environment.

Use this option only when the author information genuinely needs to be different.

### 4.9. Skip Commit Hooks

```
git commit --no-verify -m "Emergency fix"
```

Skips configured `pre-commit` and `commit-msg` hooks.

Hooks may run automated checks, formatting, tests, or message validation.

**Best practice:** Do not use this option routinely. Skipping hooks can bypass important quality checks.

### 4.10. Sign a Commit

```
git commit -S -m "Add authentication"
```

Signs the commit using your configured signing key.

Commit signing can help verify the authenticity of a commit.

The signing key must be configured before this option can work.

To inspect a commit's signature information, use:

```
git log --show-signature -1
```

### 4.11. Create a Commit with a Specific Date

Git supports setting author and committer dates through environment variables.

For example, on Linux or macOS:

```
GIT_AUTHOR_DATE="2026-01-15T10:00:00" \
GIT_COMMITTER_DATE="2026-01-15T10:00:00" \
git commit -m "Update documentation"
```

This is an advanced operation.

Changing commit dates can make repository history confusing, so use it only when there is a legitimate reason.

## 5. Examples

### Example 1: Create Your First Commit

Initialize a repository:

```
git init my-project
cd my-project
```

Create a file:

```
echo "# My Project" > README.md
```

Stage the file:

```
git add README.md
```

Create the commit:

```
git commit -m "Initial commit"
```

Git records the initial snapshot of your project.

### Example 2: Modify a File and Create a Commit

Modify `README.md`.

Then run:

```
git add README.md
git commit -m "Update project description"
```

The changes are now recorded in the repository history.

### Example 3: Commit Multiple Files

Suppose you modified three files:

```
README.md
index.html
style.css
```

Stage the files:

```
git add README.md index.html style.css
```

Create one commit:

```
git commit -m "Update project layout"
```

All staged changes are included in the same commit.

### Example 4: Commit Tracked Changes Without Running `git add` Separately

Modify an existing tracked file:

```
# Edit README.md
```

Then run:

```
git commit -a -m "Update README"
```

Git automatically stages the modification and creates the commit.

Remember that new untracked files are not included.

### Example 5: Amend the Latest Commit Message

Suppose you created a commit with an unclear message:

```
git commit -m "Changes"
```

You can improve it:

```
git commit --amend -m "Update project documentation"
```

The latest commit is replaced with a new commit using the improved message.

### Example 6: Add a Missing File to the Latest Commit

Suppose you created a commit but forgot to include a related file.

Stage the missing file:

```
git add config.json
```

Then amend the latest commit:

```
git commit --amend --no-edit
```

The latest commit is replaced with a version that includes the additional staged change.

### Example 7: Inspect the Commit After Creating It

Create a commit:

```
git add README.md
git commit -m "Update README"
```

Inspect the latest commit:

```
git show HEAD
```

Or display a shorter summary:

```
git log --oneline -1
```

## 6. Common Errors

### 6.1. Nothing to Commit

Example:

```
nothing to commit, working tree clean
```

This means Git has no staged changes to record and no other changes that it reports as pending.

**Possible causes:**

- You have not modified any tracked files.
    
- You have not staged your changes.
    
- Your changes have already been committed.
    
- New files are still untracked.
    

**Solution:**

Check the repository status:

```
git status
```

Stage the intended changes:

```
git add <file>
```

Then commit:

```
git commit -m "Describe your changes"
```

### 6.2. Author Identity Unknown

Example:

```
Author identity unknown

*** Please tell me who you are.
```

Git needs a name and email address to identify the author and committer.

**Solution:**

Configure your identity globally:

```
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
```

Or configure it only for the current repository:

```
git config user.name "Your Name"
git config user.email "you@example.com"
```

Verify the configuration:

```
git config user.name
git config user.email
```

Use an appropriate email address for your development identity.

### 6.3. Commit Message Is Empty

If you run:

```
git commit
```

and close the editor without entering a valid message, Git cancels the commit.

**Solution:**

Run the command again with a message:

```
git commit -m "Add user profile page"
```

### 6.4. Accidentally Committed the Wrong Files

If you have not shared the commit, you may be able to amend it.

First, inspect the latest commit:

```
git show --stat HEAD
```

If you need to remove a file from the latest commit while preserving its working-directory content:

```
git rm --cached unwanted-file.txt
git commit --amend --no-edit
```

This removes the file from the replacement commit but keeps the local file.

**Warning:** Amending rewrites the latest commit. Be especially careful if it has already been pushed or shared.

### 6.5. Commit Was Created but Is Not on GitHub

Creating a commit does not automatically send it to the remote repository.

**Solution:**

Push the commit:

```
git push origin main
```

Replace `main` with your actual branch name if necessary.

### 6.6. Commit Hook Failed

A configured hook may reject a commit because of formatting problems, failed tests, or an invalid commit message.

**Solution:**

Read the hook's error output, correct the reported problem, and try again.

Avoid bypassing hooks with `--no-verify` unless there is a justified reason.

### 6.7. Amend Was Rejected When Pushing

If you amend a commit that has already been pushed, the local history no longer matches the remote history.

A normal push may be rejected.

If rewriting the shared branch is intentional and coordinated with collaborators, you may need:

```
git push --force-with-lease
```

**Warning:** Force-pushing can affect other collaborators. Do not use it casually, especially on shared branches.

## 7. Best Practices

1. **Write meaningful commit messages:** Explain what the commit changes.
    
2. **Keep commits focused:** Each commit should represent a logical unit of work.
    
3. **Review staged changes:** Run `git diff --cached` before committing.
    
4. **Check repository status:** Use `git status` to confirm what will be committed.
    
5. **Prefer small, understandable commits:** They are easier to review and troubleshoot.
    
6. **Use imperative commit subjects:** For example, `Add login validation` rather than `Added login validation`.
    
7. **Avoid vague messages:** Messages such as `Update`, `Changes`, or `Fix` provide little information.
    
8. **Do not commit sensitive information:** Keep passwords, tokens, private keys, and local secrets out of repository history.
    
9. **Understand** `**git commit -a**`**:** It does not include untracked files.
    
10. **Use** `**--amend**` **carefully:** Rewriting a commit that has already been shared can cause collaboration problems.
    
11. **Do not bypass hooks routinely:** Hooks often enforce useful project standards.
    
12. **Push when you are ready to share:** A local commit is not automatically available to other developers.
    

### Recommended Commit Message Format

A simple and readable format is:

```
Short summary of the change

Optional explanation of:
- What changed
- Why the change was necessary
- Any important implementation details
```

Examples of good commit messages:

```
Add user authentication
Fix navigation menu on mobile
Update installation instructions
Remove unused dependencies
Improve error handling in API requests
```

### Recommended Workflow

```
# Check repository status
git status

# Review unstaged changes
git diff

# Stage intended files
git add README.md

# Review staged changes
git diff --cached

# Create a commit
git commit -m "Update project documentation"

# Inspect the latest commit
git show HEAD

# Push changes when ready
git push origin main
```

|---|---|

|`git log --oneline`|Display a compact commit history.|
|`git push origin main`|Push local commits to the remote `main` branch.|

## 11. Final Summary

The `git commit` command records staged changes as a new snapshot in your repository's history.

Commits allow you to track project development, understand previous changes, and maintain a reliable version history.

The most important commands to remember are:

```
# Create a commit
git commit -m "Initial commit"

# Automatically stage tracked changes and commit
git commit -a -m "Update documentation"

# Amend the latest commit
git commit --amend

# Amend without changing the message
git commit --amend --no-edit

# Create an empty commit
git commit --allow-empty -m "Trigger deployment"

# Inspect the latest commit
git show HEAD

# Push commits to a remote repository
git push origin main
```

**Key takeaway:** Use `git commit` to save staged changes as meaningful snapshots in your project's history. Good commits make your project easier to understand, maintain, review, and collaborate on.
