## Overview

Docker workflow means the typical sequence of steps developers use to:

1. Find or create an image
    
2. Build or pull the image
    
3. Run a container
    
4. Work inside the container
    
5. Inspect and monitor the container
    
6. Stop the container
    
7. Remove the container when it is no longer needed
    

Understanding the workflow is important because Docker is not just a collection of commands.

The commands work together as a process.

---

# 1. The Basic Docker Workflow

A simple Docker workflow looks like this:

```text
Dockerfile
    │
    │ docker build
    ▼
Docker Image
    │
    │ docker run
    ▼
Docker Container
    │
    ├── docker exec
    ├── docker logs
    ├── docker inspect
    ├── docker stats
    │
    │ docker stop
    ▼
Stopped Container
    │
    │ docker rm
    ▼
Removed Container
```

Another common workflow starts with an existing image:

```text
Docker Hub
    │
    │ docker pull
    ▼
Docker Image
    │
    │ docker run
    ▼
Docker Container
```

# 3. Step 1 — Choose an Image

Before running a container, you need an image.

You have two main choices:

### Option 1 — Pull an existing image

```bash
docker pull nginx
```

Docker downloads the image from a registry such as Docker Hub.

### Option 2 — Build your own image

```bash
docker build -t my-app .
```

The image is built from a `Dockerfile`.

---

# 4. Step 2 — Check Available Images

List images on your computer:

```bash
docker image ls
```

Example:

```text
REPOSITORY   TAG       IMAGE ID       CREATED       SIZE
nginx        latest    abc123456789   2 days ago    192MB
mysql        8         def987654321   3 days ago    813MB
```

You can also use:

```bash
docker images
```

Both commands are commonly used.

---

# 5. Step 3 — Run a Container

Once an image exists, create and start a container:

```bash
docker run nginx
```

Docker performs several actions:

```text
Docker Image
     ↓
Create Container
     ↓
Start Container
     ↓
Run Main Process
```

A more useful example:

```bash
docker run -d --name web-server nginx
```

Here:

```text
docker run
    ↓
-d
    ↓
Run in background
    ↓
--name web-server
    ↓
Give container a name
    ↓
nginx
    ↓
Image
```

---

# 6. Step 4 — Map Ports

Containers have their own network environment.

Suppose nginx listens on port `80` inside the container.

You can expose it through port `8080` on your computer:

```bash
docker run -d \
  --name web-server \
  -p 8080:80 \
  nginx
```

The format is:

```text
-p HOST_PORT:CONTAINER_PORT
```

So:

```text
8080:80
```

means:

```text
Computer
Port 8080
    │
    ▼
Docker Container
Port 80
```

You can then access:

```text
http://localhost:8080
```

---

# 7. Step 5 — Check Running Containers

Use:

```bash
docker ps
```

Example:

```text
CONTAINER ID   IMAGE   COMMAND   STATUS         PORTS
abc123         nginx   ...       Up 2 minutes   0.0.0.0:8080->80/tcp
```

This shows currently running containers.

To see all containers:

```bash
docker ps -a
```

This includes:

```text
Running
Stopped
Exited
Created
```

---

# 8. Step 6 — Check Container Logs

Applications inside containers produce logs.

View them with:

```bash
docker logs web-server
```

Follow logs continuously:

```bash
docker logs -f web-server
```

The `-f` means:

```text
follow
```

It keeps the terminal attached to the log output.

Stop following with:

```text
Ctrl + C
```

This does **not** normally stop the container.

---

# 9. Step 7 — Inspect the Container

Use:

```bash
docker inspect web-server
```

This provides detailed information about the container.

It can show information about:

- Container ID
    
- Image
    
- Network
    
- IP address
    
- Ports
    
- Environment variables
    
- Mounts
    
- Runtime configuration
    
- State
    

For example:

```bash
docker inspect web-server
```

produces JSON output.

You can also extract specific information.

For example:

```bash
docker inspect -f '{{.State.Status}}' web-server
```

Possible result:

```text
running
```

---

# 10. Step 8 — Execute Commands Inside the Container

You can open a shell inside a running container:

```bash
docker exec -it web-server /bin/sh
```

Depending on the image, you may also use:

```bash
docker exec -it web-server /bin/bash
```

Once inside:

```bash
pwd
```

```bash
ls
```

```bash
ps
```

You are now working inside the container.

Exit with:

```bash
exit
```

---

# 11. Step 9 — Monitor the Container

Docker provides resource information.

Use:

```bash
docker stats
```

Example:

```text
CONTAINER    CPU %    MEM USAGE / LIMIT
web-server   0.20%    12MiB / 2GiB
```

You can monitor:

- CPU usage
    
- Memory usage
    
- Network usage
    
- Block I/O
    
- Process information
    

For a specific container:

```bash
docker stats web-server
```

---

# 12. Step 10 — Stop the Container

When you are finished:

```bash
docker stop web-server
```

The container becomes stopped.

Important:

```text
Stop ≠ Delete
```

The container still exists.

Check:

```bash
docker ps -a
```

You may see:

```text
web-server   Exited
```

---

# 13. Step 11 — Start a Stopped Container

If you stopped a container and want to use the same container again:

```bash
docker start web-server
```

The workflow becomes:

```text
Running
   ↓
docker stop
   ↓
Stopped
   ↓
docker start
   ↓
Running
```

You do not need to create a new container every time.

---

# 14. Stop vs Remove

These commands are different.

### Stop

```bash
docker stop web-server
```

Stops the container.

### Remove

```bash
docker rm web-server
```

Deletes the container.

Think:

```text
docker stop
    ↓
Container still exists

docker rm
    ↓
Container is deleted
```

# 16. Building Your Own Image Workflow

Docker is also commonly used with a `Dockerfile`.

The workflow becomes:

```text
Write Dockerfile
      ↓
docker build
      ↓
Docker Image
      ↓
docker run
      ↓
Container
      ↓
Test
      ↓
Fix Dockerfile
      ↓
Build Again
      ↓
Run Again
```

Example Dockerfile:

```dockerfile
FROM nginx:alpine

COPY index.html /usr/share/nginx/html/index.html
```

Build:

```bash
docker build -t my-website .
```

Check the image:

```bash
docker image ls
```

Run it:

```bash
docker run -d \
  --name my-website \
  -p 8080:80 \
  my-website
```

Check:

```bash
docker ps
```

# 17. The Development Workflow

During application development, you may repeatedly perform this process:

```text
Write Code
    ↓
Write Dockerfile
    ↓
Build Image
    ↓
Run Container
    ↓
Test Application
    ↓
Check Logs
    ↓
Find Problem
    ↓
Modify Code/Dockerfile
    ↓
Build Again
    ↓
Run Again
```

For example:

```bash
docker build -t my-app .
```

```bash
docker run -d --name my-app-container my-app
```

Check:

```bash
docker logs my-app-container
```

If something is wrong:

```bash
docker stop my-app-container
docker rm my-app-container
```

Then rebuild:

```bash
docker build -t my-app .
```

# 18. Docker Workflow With Docker Compose

For applications with multiple services, Docker Compose provides a better workflow.

For example:

```text
        Docker Compose
              │
       ┌──────┼──────┐
       ↓      ↓      ↓
      Web   API   Database
       │      │      │
       └──────┼──────┘
              ↓
          Application
```

A typical workflow is:

```bash
docker compose up -d
```

Check services:

```bash
docker compose ps
```

View logs:

```bash
docker compose logs
```

Follow logs:

```bash
docker compose logs -f
```

Stop and remove the Compose application:

```bash
docker compose down
```

The workflow becomes:

```text
compose.yaml
     ↓
docker compose up
     ↓
Multiple Containers
     ↓
Test Application
     ↓
docker compose logs
     ↓
docker compose down
```

# 19. Docker Workflow in Production

A production workflow is more controlled.

A simplified example:

```text
Developer
    ↓
Source Code
    ↓
Dockerfile
    ↓
Build Image
    ↓
Test Image
    ↓
Security Scan
    ↓
Tag Image
    ↓
Push to Registry
    ↓
Deploy
    ↓
Run Containers
    ↓
Monitor
```

For example:

```bash
docker build -t my-app:1.0 .
```

Test:

```bash
docker run --rm my-app:1.0
```

Tag:

```bash
docker tag my-app:1.0 username/my-app:1.0
```

Push:

```bash
docker push username/my-app:1.0
```

A deployment environment can then pull the image:

```bash
docker pull username/my-app:1.0
```

And run it:

```bash
docker run -d username/my-app:1.0
```

# 20. Image vs Container Workflow

Remember the relationship:

```text
IMAGE
  │
  │ docker run
  ▼
CONTAINER
```

One image can create multiple containers:

```text
             nginx image
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
    container1 container2 container3
```

For example:

```bash
docker run -d --name web1 nginx
```

```bash
docker run -d --name web2 nginx
```

Both containers use the same image.

# 21. A Container Is Disposable

One of the most important Docker ideas is:

> Containers should generally be treated as replaceable environments.

Instead of manually repairing a broken container forever:

```text
Broken Container
       ↓
Stop
       ↓
Remove
       ↓
Build/Pull Correct Image
       ↓
Create New Container
```

This is one reason Docker is useful.

The image describes how the environment should be created.

The container is an instance of that image.

---

# 22. Data Requires Special Attention

Containers have writable storage, but important data should not normally depend only on the container's writable layer.

For persistent data, use volumes or bind mounts.

For example:

```text
Container
    │
    │
    ▼
Docker Volume
    │
    ▼
Persistent Data
```

This is especially important for databases.

For example:

```text
MySQL Container
      │
      ▼
MySQL Data Volume
      │
      ▼
Data survives container replacement
```

# 23. Example Database Workflow

A simplified MySQL workflow:

```bash
docker run -d \
  --name mysql-db \
  -e MYSQL_ROOT_PASSWORD=example \
  -v mysql-data:/var/lib/mysql \
  mysql:8
```

Check:

```bash
docker ps
```

View logs:

```bash
docker logs mysql-db
```

Open MySQL:

```bash
docker exec -it mysql-db mysql -u root -p
```

Stop:

```bash
docker stop mysql-db
```

Start again:

```bash
docker start mysql-db
```

The container can be restarted while the named volume keeps the database data.

# 24. A Useful Troubleshooting Workflow

When a container does not work, do not randomly run commands.

Follow a process.

```text
Container Problem
       ↓
docker ps -a
       ↓
Check Status
       ↓
docker logs
       ↓
Check Configuration
       ↓
docker inspect
       ↓
Check Ports
       ↓
Check Environment
       ↓
Check Volumes
       ↓
Check Network
       ↓
Fix Problem
       ↓
Test Again
```

Useful commands:

```bash
docker ps -a
```

```bash
docker logs container-name
```

```bash
docker inspect container-name
```

```bash
docker stats
```

```bash
docker port container-name
```

```bash
docker exec -it container-name /bin/sh
```

# 30. Key Takeaways

Remember these ideas:

1. Docker workflow is a sequence, not just individual commands.
    
2. Images are used to create containers.
    
3. `docker pull` downloads an existing image.
    
4. `docker build` creates an image from a Dockerfile.
    
5. `docker run` creates and starts a container.
    
6. `docker ps` shows running containers.
    
7. `docker ps -a` shows all containers.
    
8. `docker logs` helps troubleshoot applications.
    
9. `docker exec` lets you run commands inside containers.
    
10. `docker inspect` shows detailed configuration.
    
11. `docker stop` stops a container.
    
12. `docker start` starts a stopped container.
    
13. `docker rm` removes a container.
    
14. Containers can be replaced; important data should use appropriate persistent storage.
    
15. Docker Compose extends the workflow to multiple services.
    
16. Production workflows usually include testing, security checks, image tagging, registries, deployment, and monitoring.
