**Git is a distributed version control system (VCS)** used to track changes in files, especially source code, over time.

In simple terms:

> **Git lets you save versions of your project, see what changed, go back to older versions, work on different features safely, and collaborate with other developers.**

Git was originally created by **Linus Torvalds in 2005** to help manage the Linux kernel source code.

---

## Why do we need Git?

Imagine you are working on a project and manually create copies:

```text
project/
├── project-final/
├── project-final-v2/
├── project-final-v3/
├── project-final-new/
└── project-final-really-final/
```

This quickly becomes difficult to manage.

With Git, you can keep one project and record its history:

```text
Project
   │
   ├── Commit 1
   ├── Commit 2
   ├── Commit 3
   └── Commit 4
```

Each **commit** represents a saved version of your project.

You can inspect the history, compare versions, and restore previous work when necessary.

---

## Git in one sentence

A useful mental model is:

> **Git is a tool that records the history of your project as a series of snapshots called commits.**

For example:

```text
Working files
     │
     ▼
   git add
     │
     ▼
Staging Area
     │
     ▼
  git commit
     │
     ▼
Repository history
```

## What can Git track?

Git can track changes to many types of files:

```text
project/
├── index.html
├── app.js
├── styles.css
├── README.md
└── config.json
```

It can record things such as:

- Files being created
    
- Files being modified
    
- Files being deleted
    
- Files being renamed
    
- Changes between versions
    
- Who made a commit
    
- When a commit was made
    
- The relationship between commits
    

Git is particularly popular for **software development**, but it can also be used for documentation, configuration files, notes, and other text-based projects.

# Git's basic architecture

Git is built around several important concepts:

```text
                 Git Repository
                      │
                      ▼
              ┌───────────────┐
              │ Commit History │
              └───────────────┘
                      ▲
                      │
                  git commit
                      │
                      ▲
              ┌───────────────┐
              │ Staging Area  │
              └───────────────┘
                      ▲
                      │
                   git add
                      │
                      ▲
              ┌───────────────┐
              │ Working Tree  │
              └───────────────┘
```

The three most important areas for beginners are:

### 1. Working Tree

The files you are currently working on.

For example:

```text
index.html
app.js
style.css
```

You edit these files normally.

### 2. Staging Area

A preparation area where you select which changes should go into the next commit.

```bash
git add app.js
```

### 3. Repository

The Git database containing your commits and project history.

```bash
git commit -m "Add login functionality"
```

# What is a commit?

A **commit** is a recorded snapshot of changes.

For example:

```text
A ─── B ─── C
```

Where:

```text
A = Initial project
B = Add navigation
C = Add authentication
```

Each commit has an identifier, commonly represented by a SHA-1 or SHA-256 object ID depending on the repository's configuration.

You can inspect commits with:

```bash
git log
```

---

# Git is distributed

The word **distributed** is important.

With Git, a normal clone contains the repository's history locally.

For example:

```text
             Remote Repository
                  GitHub
                     │
                  git clone
                     │
                     ▼
              Local Repository
                     │
             ┌───────┴───────┐
             ▼               ▼
        Make changes      View history
             │
             ▼
          Commit
```

You can create commits even when you are offline because Git's core version-control operations happen locally.

# Git vs GitHub

A common beginner misconception is:

> Git and GitHub are the same thing.

They are not.

**Git** is the version-control software.

**GitHub** is a platform that can host Git repositories and provide collaboration features.

Think of it like:

```text
Git
│
├── Version control
├── Commits
├── Branches
├── Merging
├── Rebase
└── Local repositories

GitHub
│
├── Host Git repositories
├── Pull Requests
├── Code Review
├── Issues
├── Actions
└── Collaboration
```

You can use **Git without GitHub**.

You can also use Git with other hosting platforms such as GitLab, Bitbucket, or a self-hosted Git server.

# A simple Git workflow

A typical local workflow looks like this:

```text
1. Create/modify files
          │
          ▼
2. Check changes
       git status
          │
          ▼
3. Stage changes
        git add
          │
          ▼
4. Create commit
      git commit
          │
          ▼
5. Inspect history
       git log
```

When collaborating with a remote repository:

```text
                 Remote
              Repository
             /          \
         push            fetch
           ↑                ↓
           │                │
      Local Repository ──────┘
              │
              ▼
         Working Tree
```

Common commands include:

```bash
git status
git add .
git commit -m "Add feature"
git push
git fetch
git pull
```

# What makes Git powerful?

Git provides several capabilities that become especially useful as projects grow.

### Version history

You can see how your project evolved.

```bash
git log
```

### Branching

You can work on a feature independently:

```bash
git switch -c login-feature
```

```text
main
 │
 ├── A ─── B ─── C
             \
              D ─── E
                   ↑
              login-feature
```

### Merging

You can bring work from one branch into another:

```bash
git switch main
git merge login-feature
```

### Comparing changes

```bash
git diff
```

### Recovering work

Git can often help recover commits or changes that appear to have been lost.

One important recovery tool is:

```bash
git reflog
```

# Git's core idea

The most important concept to understand is that Git doesn't primarily think in terms of "files and folders."

At its core, Git stores **objects** and connects commits into a history.

A simplified model is:

```text
Commit
  │
  ├── Parent commit
  ├── Author
  ├── Message
  └── Tree
       │
       ├── file.txt → Blob
       ├── app.js   → Blob
       └── src/     → Tree
```

This object model is why topics such as **commits, trees, blobs, references, HEAD, and hashes** become important when learning Git internals.

### The key terms to remember

|Term|Meaning|
|---|---|
|**Git**|Distributed version control system|
|**Repository**|Git database containing project history|
|**Working Tree**|Files you currently work on|
|**Staging Area**|Changes selected for the next commit|
|**Commit**|Recorded snapshot of project state|
|**Branch**|Movable pointer to a line of development|
|**HEAD**|Reference to the currently checked-out position|
|**Remote**|Reference to another repository|
|**GitHub**|Platform for hosting and collaborating around Git repositories|

**In short:** Git gives you a reliable history of your project and tools for **tracking, branching, merging, collaborating, and recovering changes**.
