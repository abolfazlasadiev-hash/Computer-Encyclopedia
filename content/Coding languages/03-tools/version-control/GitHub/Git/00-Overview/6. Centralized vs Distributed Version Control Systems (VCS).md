Version Control Systems are commonly divided into two major models:

1. **Centralized Version Control Systems (CVCS)**
    
2. **Distributed Version Control Systems (DVCS)**
    

The main difference is **where the repository and its history are stored and how developers work with them**.

---

# 1. Centralized VCS (CVCS)

In a **Centralized Version Control System**, a central server stores the primary repository and its history.

Developers connect to that server to obtain and share changes.

```text
                   Central Server
                 ┌────────────────┐
                 │   Repository   │
                 │    History     │
                 └───────┬────────┘
                         │
          ┌──────────────┼──────────────┐
          │              │              │
          ▼              ▼              ▼
     Developer A    Developer B    Developer C
       Working        Working        Working
        Copy           Copy           Copy
```

### Examples

- Subversion (SVN)
    
- CVS
    
- Perforce
    

---

## How Centralized VCS Works

A developer typically works with files obtained from the central repository:

```text
Central Repository
        │
        ▼
   Get Latest Files
        │
        ▼
   Make Changes
        │
        ▼
   Commit Changes
        │
        ▼
Central Repository
```

The central server plays a critical role in the team's workflow.

---

# 2. Distributed VCS (DVCS)

In a **Distributed Version Control System**, each developer has a local repository containing project history.

```text
                    Remote Repository
                           │
              ┌────────────┼────────────┐
              │            │            │
              ▼            ▼            ▼
         Developer A   Developer B   Developer C
          Local Repo    Local Repo    Local Repo
```

Each local repository can contain its own commit history.

### Examples

- Git
    
- Mercurial
    

---

## How Distributed VCS Works

A typical Git workflow:

```text
Remote Repository
       │
       │ git clone
       ▼
Local Repository
       │
       ▼
Make Changes
       │
       ▼
git add
       │
       ▼
git commit
       │
       ▼
Local History
       │
       │ git push
       ▼
Remote Repository
```

A developer can create commits locally without immediately communicating with a remote server.

---

# 3. The Main Architectural Difference

## Centralized VCS

```text
             ONE CENTRAL REPOSITORY
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       User A      User B      User C
      Working     Working     Working
       Copy        Copy        Copy
```

The central repository is the main location for shared history.

---

## Distributed VCS

```text
                 REMOTE REPOSITORY
                         │
            ┌────────────┼────────────┐
            ▼            ▼            ▼
       LOCAL REPO    LOCAL REPO    LOCAL REPO
        User A        User B        User C
            │            │            │
         History      History      History
```

Every developer has a repository and local history.

---

# 4. Centralized vs Distributed Comparison

|Feature|Centralized VCS|Distributed VCS|
|---|---|---|
|Repository model|Central server|Multiple full repositories|
|Local history|Often more limited|Full history in a typical clone|
|Offline work|More limited|Many operations work offline|
|Local commits|Workflow depends on central server|Fully supported|
|Server dependency|Higher|Lower for local work|
|Collaboration|Centralized|Flexible|
|Network usage|Often required more frequently|Mainly needed for synchronization|
|Local operations|Can depend more on server|Usually fast and local|
|Examples|SVN, CVS, Perforce|Git, Mercurial|

---

# 5. Working Offline

This is one of the most important differences.

## Centralized VCS

If the central server is unavailable:

```text
Developer
    │
    X
    │
Central Server Unavailable
```

Some workflows and operations may be significantly limited because they depend on the central server.

---

## Distributed VCS

With Git, you have a local repository.

```text
Your Computer
│
├── Working Files
│
└── Local Git Repository
    │
    ├── Commit A
    ├── Commit B
    └── Commit C
```

You can perform many operations offline:

```bash
git status
git add .
git commit -m "Add feature"
git log
git diff
git branch
```

You need network access primarily to synchronize with another repository:

```bash
git fetch
git pull
git push
```

---

# 6. Commit Model

## Centralized VCS

A commit commonly involves communicating changes to the central repository.

```text
Developer
    │
    │ Commit
    ▼
Central Server
    │
    ▼
Shared History Updated
```

---

## Distributed VCS

Git separates local commits from sharing those commits.

```text
Developer
    │
    │ git commit
    ▼
Local Repository
    │
    │ git push
    ▼
Remote Repository
```

This distinction is extremely important.

> **A Git commit does not automatically send your changes to GitHub or GitLab.**

You normally create the commit locally first, then push it to a remote repository.

---

# 7. Server Failure

## Centralized VCS

```text
        Server
          │
          X
      Unavailable
          │
    ┌─────┴─────┐
    ▼           ▼
Developer A  Developer B
```

A central server outage can significantly disrupt normal team operations.

---

## Distributed VCS

```text
Remote Server
     X
Unavailable

Developer A
Local Repository
     │
     ├── Commit
     ├── Branch
     ├── Diff
     └── History
```

Developers can continue performing many local operations.

Once the remote becomes available, they can synchronize their work.

---

# 8. Collaboration Model

## Centralized VCS

```text
       Developer A
            │
            ▼
      Central Server
            ▲
            │
       Developer B
```

The central server is the main collaboration point.

---

## Distributed VCS

```text
       Developer A
       Local Repo
            │
            │
       Synchronize
            │
            ▼
      Remote Repository
            ▲
            │
       Synchronize
            │
       Developer B
       Local Repo
```

Distributed systems can also support more flexible repository-to-repository workflows.

---

# 9. Branching

Both centralized and distributed VCS tools can support branching.

However, distributed systems such as Git are especially known for lightweight local branching and flexible workflows.

Git branching:

```text
main

A ─── B ─── C
       \
        D ─── E
          feature
```

You can create a branch:

```bash
git branch feature
```

Or:

```bash
git switch -c feature
```

The branch exists locally until you decide to share it.

# 10. A Real-World Example

Imagine three developers working on a project.

## Centralized Model

```text
                Central Repository
                       │
             ┌─────────┼─────────┐
             │         │         │
             ▼         ▼         ▼
          Alice       Bob      Charlie
```

Developers generally interact with the same central repository.

---

## Distributed Model

```text
                   GitHub / GitLab
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
        Alice            Bob          Charlie
      Local Git       Local Git      Local Git
      Repository      Repository     Repository
```

Each developer has a local Git repository.

A remote platform acts as a shared synchronization and collaboration point.

---

# 11. Advantages of Centralized VCS

### Simpler central model

There is usually one obvious shared repository.

```text
Everyone
    │
    ▼
Central Repository
```

### Centralized administration

Organizations can manage access and permissions from a central location.

### Familiar workflow

The model can be easier to understand initially:

```text
Get files
   ↓
Edit
   ↓
Commit to server
```

---

# 12. Advantages of Distributed VCS

### Work offline

Many operations do not require a network connection.

### Full local history

A typical Git clone contains repository history locally.

### Fast local operations

Commands such as:

```bash
git log
git diff
git commit
```

primarily operate locally.

### Flexible branching

Git makes it easy to create and work with branches.

### Flexible workflows

Teams can use different repository models and collaboration strategies.

---

# 13. Disadvantages

## Centralized VCS

- Greater dependence on the central server
    
- Offline work can be more limited
    
- Server outages can disrupt collaboration
    
- Network communication may be required more frequently
    

---

## Distributed VCS

- More concepts for beginners to learn
    
- Remotes and synchronization can initially be confusing
    
- History rewriting requires care in collaborative repositories
    
- Multiple branches and repositories can increase complexity
    

---

# 14. Git as a Distributed VCS

Git follows the distributed model.

```text
                Remote Repository
                       │
                       │
                 git clone
                       │
                       ▼
                Local Repository
                       │
              ┌────────┼────────┐
              ▼        ▼        ▼
           Commits   Branches   History
                       │
                       ▼
                  git push
                       │
                       ▼
                Remote Repository
```

The key idea is:

> **Your local Git repository is a real repository, not just a temporary copy of files.**

You can create commits and maintain history locally.

---

# 15. Easy Analogy

Think of a **Centralized VCS** like a shared office document system:

```text
                One Main Server
                      │
            Everyone connects
```

Think of a **Distributed VCS** like every developer having a complete copy of the project's history:

```text
Developer A → Complete history
Developer B → Complete history
Developer C → Complete history
```

They synchronize their work when necessary.

# Summary

```text
                 VERSION CONTROL SYSTEMS
                           │
             ┌─────────────┴─────────────┐
             │                           │
             ▼                           ▼
      CENTRALIZED VCS              DISTRIBUTED VCS
             │                           │
       Central Server               Local Repositories
             │                           │
      SVN, CVS, Perforce           Git, Mercurial
             │                           │
      Higher server dependence      More local autonomy
```

## The most important difference

> **Centralized VCS relies primarily on a central repository for shared version control, while Distributed VCS gives each developer a local repository with its own history that can synchronize with other repositories.**

### In the context of Git:

```text
git commit
    │
    ▼
Local Repository

git push
    │
    ▼
Remote Repository
```

This separation between **committing locally** and **sharing remotely** is one of the most important concepts in understanding Git.
