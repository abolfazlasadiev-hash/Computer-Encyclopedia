## 1. Overview

A **Docker image** is a packaged, read-only template used to create Docker containers.

For example:

```bash
docker run nginx
```

Docker uses the `nginx` image to create a container.

The basic relationship is:

```text
Docker Image
     ↓
docker run
     ↓
Docker Container
```

A simple way to think about it:

```text
Image      = Template
Container  = Running instance created from the template
```

---

# 2. What Is a Docker Image?

A Docker image contains the files, libraries, configuration, and metadata needed to create a container.

For example, an application image might contain:

```text
Application
    +
Runtime
    +
Libraries
    +
Configuration
    +
Operating-system files
```

A container is created from that image.

---

# 3. Image vs Container

This is one of the most important Docker concepts.

|Image|Container|
|---|---|
|Template|Instance|
|Read-only|Has a writable container layer|
|Used to create containers|Created from an image|
|Can be stored in a registry|Runs on Docker Engine|
|Does not normally change when a container runs|Has its own runtime state|

Think about it like this:

```text
IMAGE
  │
  ├── Container 1
  ├── Container 2
  └── Container 3
```

One image can be used to create many containers.

---

# 4. Example

Suppose you have the Nginx image:

```text
nginx
```

You can create one container:

```bash
docker run -d --name web1 nginx
```

You could also create another:

```bash
docker run -d --name web2 nginx
```

Both containers were created from the same image:

```text
             nginx image
                 │
          ┌──────┴──────┐
          ↓             ↓
       web1            web2
     container       container
```

The `docker pull` command downloads an image.

# 8. What Does `latest` Mean?

When you run:

```bash
docker pull nginx
```

Docker normally interprets the image reference as:

```text
nginx:latest
```

The part after `:` is called the **tag**.

```text
nginx:latest
  │      │
  │      └── Tag
  │
  └── Repository
```

Important:

> `latest` is a tag name. It does not inherently mean "the newest version" in every technical sense.

The tag can be moved by the image publisher.

For reproducible deployments, explicit version tags or digests are generally preferable.

# 16. Image Architecture

Images contain more than just application files.

A simplified model is:

```text
Docker Image
│
├── Application files
├── Libraries
├── Runtime files
├── Configuration
├── Metadata
└── Layers
```

For example, a Node.js application image might contain:

```text
Node.js runtime
       +
Application dependencies
       +
Application source
       +
Configuration
```

---

# 17. Images Are Read-Only Templates

A Docker image is treated as immutable/read-only when containers are created from it.

For example:

```text
             nginx image
                 │
        ┌────────┼────────┐
        ↓        ↓        ↓
      web1      web2      web3
```

The containers can have their own writable runtime state without modifying the underlying image itself.

---

# 18. Container Writable Layer

When a container starts, Docker adds a writable layer above the image's read-only layers.

Simplified:

```text
Container
│
├── Writable container layer
│
├── Image layer
├── Image layer
├── Image layer
└── Image layer
```

This helps Docker share common image data between containers.

Important:

> Data written only to a container's writable layer is tied to that container's lifecycle.

For persistent application data, use volumes or bind mounts where appropriate.

---

# 19. Image Layers

Docker images are normally composed of multiple layers.

Simplified:

```text
Application Layer
       ↓
Dependency Layer
       ↓
Runtime Layer
       ↓
Base Image Layer
```

Each layer represents filesystem changes associated with image construction.

This layered design provides important benefits:

- Reuse
    
- Caching
    
- Faster builds
    
- Efficient storage
    
- Smaller transfers when layers can be reused
    

We will study image layers in more detail later.

---

# 20. Image Reuse

Suppose you have:

```text
nginx image
```

and create:

```text
web1
web2
web3
```

Docker does not need three completely independent copies of every image layer.

Instead, containers can share the image's read-only layers.

Conceptually:

```text
             Shared Image Layers
                    │
          ┌─────────┼─────────┐
          ↓         ↓         ↓
        web1      web2      web3
```

This is one reason Docker can create containers quickly.

# 21. Pull vs Run

A common beginner question:

### What does `docker pull` do?

```bash
docker pull nginx
```

It downloads the image.

It does **not** create a running container.

### What does `docker run` do?

```bash
docker run nginx
```

It creates and starts a container from the image.

Simplified:

```text
docker pull nginx
       ↓
Download image


docker run nginx
       ↓
Use image
       ↓
Create container
       ↓
Start container
```

---

# 22. `docker run` Can Pull Automatically

If the requested image is not available locally, Docker can often pull it automatically when you run:

```bash
docker run nginx
```

Conceptually:

```text
Is image available locally?
        │
    ┌───┴───┐
   YES      NO
    │        │
    ↓        ↓
 Create    Pull image
 container    ↓
    │       Create
    └───→  container
```

This means you do not always need to run `docker pull` first.

However, explicitly pulling an image can be useful when you want to download or inspect it before creating a container.

# 23. Removing Images

You can remove an image with:

```bash
docker rmi nginx
```

The modern management-command form is:

```bash
docker image rm nginx
```

Before removing an image, check:

```bash
docker image ls
```

and:

```bash
docker ps -a
```

An image may be referenced by existing containers, so Docker may refuse to remove it until those references are handled.

---

# 24. Force Removing an Image

Docker also provides:

```bash
docker image rm -f IMAGE
```

The `-f` option means force.

Use force carefully.

Do not use destructive options simply because they make a command succeed.

First understand what Docker is protecting you from.

---

# 25. Dangling Images

Sometimes an image can become untagged.

You may see something like:

```text
<none>    <none>    abc123...
```

These are commonly called **dangling images**.

You can inspect them with:

```bash
docker image ls
```

You can remove unused image data with pruning commands, but understand exactly what will be deleted before confirming.

---

# 26. Image Pruning

Docker provides:

```bash
docker image prune
```

This can remove dangling images.

Docker may ask for confirmation:

```text
Are you sure you want to continue? [y/N]
```

Be careful with cleanup commands.

A broader command is:

```bash
docker image prune -a
```

This can remove images that are not currently associated with containers, not merely dangling images.

Use `-a` cautiously.

---

# 27. Image Digests

Tags can change.

For stronger image identity, Docker also supports **digests**.

An image digest looks conceptually like:

```text
sha256:abcdef123456...
```

A digest identifies a specific image content.

For example:

```text
nginx@sha256:...
```

This is different from:

```text
nginx:latest
```

because a tag can be moved to another image, while a digest identifies specific content.

---

# 28. Tags vs Digests

|Tag|Digest|
|---|---|
|Human-friendly label|Content-based identifier|
|Can be moved|Identifies specific content|
|Easy to use|Better for exact pinning|
|Example: `nginx:latest`|Example: `nginx@sha256:...`|

For learning:

```text
Tag
 ↓
Friendly name
```

For reproducibility:

```text
Digest
 ↓
Specific image content
```

# 31. Image Naming

When you build an image:

```bash
docker build -t my-app .
```

The `-t` option gives the image a name/tag.

You can use:

```bash
docker image ls
```

to see it.

For example:

```text
REPOSITORY   TAG       IMAGE ID
my-app       latest    abc123...
```

You can also specify a version:

```bash
docker build -t my-app:1.0 .
```

Now the image reference is:

```text
my-app:1.0
```

---

# 32. Multiple Tags

The same image can have multiple tags.

For example:

```text
my-app:latest
my-app:1.0
my-app:stable
```

These tags can refer to the same image content.

You can create another tag with:

```bash
docker tag my-app:1.0 my-app:stable
```

Check:

```bash
docker image ls
```

Tags are labels; they do not automatically create separate copies of the underlying image content.

# 34. Image Architecture and Platforms

Images can target different CPU architectures.

Common examples include:

```text
linux/amd64
linux/arm64
linux/arm/v7
```

You can inspect an image:

```bash
docker image inspect nginx
```

Modern Docker can also work with multi-platform images.

Conceptually:

```text
             nginx
               │
        ┌──────┴──────┐
        ↓             ↓
   linux/amd64    linux/arm64
```

Docker selects an appropriate platform variant when supported.

Platform-specific image behavior becomes especially important when moving between Intel/AMD machines, ARM machines, servers, and CI systems.

# 42. Common Beginner Mistakes

## Mistake 1 — Confusing Image and Container

Wrong mental model:

```text
Image = container
```

Better:

```text
Image = template
Container = instance
```

---

## Mistake 2 — Thinking `docker pull` Starts a Container

This:

```bash
docker pull nginx
```

downloads the image.

It does not normally start a container.

---

## Mistake 3 — Thinking Removing a Container Removes the Image

This:

```bash
docker rm my-container
```

removes the container.

The image can remain:

```bash
docker image ls
```

---

## Mistake 4 — Treating `latest` as a Permanent Version

This:

```text
nginx:latest
```

is a tag.

The tag can point to different image content over time.

---

## Mistake 5 — Deleting Images Carelessly

Commands such as:

```bash
docker image prune -a
```

can remove images you may want to keep locally.

Always understand cleanup commands before confirming them.

# 43. Image Security

```text

        ↓

        ↓
```

Do not assume that an image is safe simply because it is publicly available.
